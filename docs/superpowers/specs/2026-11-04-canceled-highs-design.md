# 취소된 신고가 기능 설계

작성일: 2026-11-04
상태: 빌더 검토 반영, 사용자 승인 대기

## 1. 무엇을, 왜

zipsise.com(수도권 아파트 실거래가)은 2026-11-04 런칭했다. 실거래가 조회 자체는 아실·호갱노노와 차이가 없다. 같은 국토부 데이터를 쓰기 때문이다. 이기려면 **남들이 전면에 내세우지 않는 질문 하나**에 가장 잘 답해야 한다. 부루팡(burupang.com)이 "사라진 매물 = 거래완료 신호" 하나로 서비스가 되는 것과 같은 방식이다.

우리가 고른 질문: **"이 신고가, 진짜였나?"**

국토부 실거래 데이터에는 2020년부터 거래 해제(취소) 여부와 해제일이 공개된다. 신고가로 신고됐다가 나중에 취소된 거래는 "집값 띄우기" 의심 사례로 늘 화제가 된다. 공공 데이터라 법적 위험이 없고, 이미 우리 DB에 들어 있다.

보는 사람은 두 부류다(사용자 답: "둘 다").

1. **단지 페이지에 온 사람**: 사거나 팔려는 단지의 최고가가 진짜 거래였는지 확인한다.
2. **밖에서 들어오는 사람**: 커뮤니티·카톡에 퍼진 "이번 주 취소된 신고가"를 보고 들어온다. 첫 유입을 만드는 쪽이 이쪽이다.

## 2. 목표 · 비목표 · 안티목표

### 목표
- 단지 페이지에서 취소된 거래, 특히 **당시 신고가였던 취소**를 한눈에 본다.
- "취소된 신고가" 모음 페이지가 있고, 맨 위에서 시선을 잡는다.
- 취소된 신고가마다 **공유용 이미지 카드**가 자동으로 만들어져, 링크를 카톡·커뮤니티에 붙이면 미리보기로 뜬다.
- 늦게 들어오는 취소(계약 후 2~6개월)도 놓치지 않는다.

### 비목표 (이번엔 안 함)
- 시세 차트에 취소 거래를 점으로 찍기(시안 C). 지금 차트는 월 평균선이라 개별 점을 얹으려면 차트를 다시 만들어야 한다.
- 지도 위 빨간 핀(시안 C 지도판).
- 알림(관심단지 취소 발생 시 푸시). 로그인·푸시가 아직 없다.
- 전월세 취소. 전월세 API에는 해제 정보가 없다.
- "자전거래" "작전" 같은 단정. 우리는 사실(신고·취소 날짜와 가격)만 보여 준다.

### 안티목표 (이러면 실패)
- 특정 단지·사람을 범죄자처럼 몰아가는 문구. 취소에는 정상적인 사유(대출 불발, 계약 해지 합의 등)도 많다. 문구는 중립.
- 취소 정보가 틀리는 것. 형식이 섞인 해제일을 그대로 쓰면 날짜가 틀리고 집계가 틀린다(4장 참조).
- 표만 있어서 아무도 눈여겨보지 않는 페이지(사용자 피드백: "눈에 들어오지가 않을 것 같은데").

## 3. 데이터에서 확인한 사실 (2026-11-04)

- 취소 정보는 2020년 거래부터 있다. 2024년 이후 거래 중 해제일이 있는 거래 41,878건.
- **`is_canceled` 플래그는 믿을 수 없다.** 예전 수집기는 플래그 없이 해제일만 넣었다. 해제일(`cancel_date`)이 기준이다. 기존 화면·집계도 이미 `cancel_date IS NULL`로 거른다.
- **해제일 형식이 섞여 있다.** 예전 수집기는 `YY.MM.DD`(예: `25.07.28`), 새 수집기는 `YYYY-MM-DD`.
- 계약 후 취소까지 걸린 기간: 30일 이내 40%, 60일 66%, 90일 81%, 180일 94%.
- **매일 수집은 이번 달·지난달만 다시 받는다.** 그래서 계약 3개월 이후에 들어오는 취소(약 1/3)는 지금 놓친다.
- 단지 상세 JSON(`v1/apt/{id}/trade.json`)에는 이미 거래별 `cancel_date`가 들어 있다. 화면 목록에도 "취소" 표시가 있다.

## 4. 결정된 것

### 4.1 "취소된 신고가"의 정의 (내 판단)
어떤 매매 거래 T가 아래를 모두 만족하면 "취소된 신고가"다.
- T의 해제일이 있다.
- 같은 단지, 같은 평형 묶음(전용면적 정수부 버림, 기존 `areaGroup`/`CAST(area AS INTEGER)`과 같은 기준)에서,
- T의 계약일 **이전**에 있었던 **취소되지 않은** 거래들의 최고가보다 T의 금액이 **높다**.
- 그 평형에 이전 거래가 하나도 없으면 신고가로 치지 않는다(비교 대상 없음).

"얼마나 튀었나" = T 금액 − 직전 최고가. 모음 페이지의 정렬 기준이다.

### 4.2 데이터 정리
- 해제일을 모두 `YYYY-MM-DD`로 맞춘다. 기존 행은 한 번 변환하고, 수집기는 이미 새 형식이다.
- `is_canceled`는 `cancel_date IS NOT NULL`과 같게 맞춘다.
- 정본 DB를 고친 뒤 R2에 올린다. 매일 수집 사이에 끼지 않게 한다.

### 4.3 늦은 취소 잡기
- 매일 수집과 별개로, **주 1회 3~6개월 전 계약월의 매매를 다시 받는다.** 83개 지역 × 4개월 = 332회 호출/주. 매매 API 하루 한도 10,000회에 여유 있음.
- 이미 있는 거래에 해제일이 새로 붙으면 기존 수집 로직(`db.py`, 해제일 갱신)이 처리한다. 바뀐 단지는 평소처럼 다시 내보낸다.

### 4.4 단지 페이지 (시안 A + B + D, 사용자 선택)
기존 `trade.json`의 `cancel_date`로 브라우저에서 계산한다. 서버·파이프라인 변경 없음.
- **A. 맨 위 경고 한 줄**: 요약 카드 안에 "최근 1년 취소된 거래 N건 · 그중 신고가였던 거래 M건". 취소가 0건이면 안 보인다. 누르면 D로 스크롤.
- **B. 평형별 시세표**: 기존 최고가는 이미 취소를 뺀 값이다. 그 평형에 **최고가보다 높은 취소 거래**가 있으면 옆에 작게 "취소된 더 높은 가격 X" 표시.
- **D. 취소된 거래 섹션**: 매매 탭에서 실거래 내역 위. 계약일 · 평형 · 층 · 가격 · 해제일 · "당시 신고가" 배지. 최신 해제일 순. 0건이면 섹션 없음.

### 4.5 모음 페이지 `/canceled` (시안 A + B, 사용자 선택)
- **맨 위 헤드라인**: "최근 7일, 신고가 N건이 신고 후 취소됐습니다". 기간은 **해제일 기준**(내 판단: 계약일 기준이면 몇 달 전 거래가 섞여 "이번 주" 느낌이 사라진다).
- 그 아래 **가장 많이 튄 3건**을 큰 숫자 카드로("+4,000만", "21일 만에 취소").
- 그 아래 전체 목록. 휴대폰은 카드, PC는 표(내 판단). 기간 탭 7일 / 30일(내 판단: 주에 따라 건수가 적을 수 있다). 지역 필터 서울/경기/인천(내 판단).
- 목록 각 줄은 단지 페이지로 링크.
- 홈 화면과 상단 메뉴에 진입점 하나("취소된 신고가").

### 4.6 공유 카드 (시안 B)
- 취소된 신고가 한 건마다 공유 주소: `/canceled/{거래id}`. 이 페이지의 OG 이미지가 어두운 배경 카드(단지명·평형, 신고된 가격 취소선, 직전 최고가, 계약일→해제일 며칠)다.
- 기존 단지 OG 이미지(`/api/og/[id]`)와 같은 방식(Node 런타임, 같은 폰트 서브셋)으로 만든다.
- 페이지 본문은 그 거래 설명 + 단지 페이지 링크 + 모음 페이지 링크. 공유 버튼(기존 `ShareButton`) 재사용.

### 4.7 모음 데이터 내보내기
- 매일 수집의 내보내기 단계에서 `v1/canceled/recent.json`을 만든다: 해제일 기준 최근 30일의 취소된 신고가 전체(단지명, 지역, 평형, 층, 금액, 직전 최고가, 계약일, 해제일, 거래 id, 단지 id). 7일 보기는 브라우저에서 거른다.
- 공유 페이지 `/canceled/{거래id}`는 30일이 지나도 열려야 한다. 그래서 거래 하나의 정보는 단지 `trade.json`에서 다시 계산한다(거래 id → 단지 id가 필요하므로 공유 주소에 단지 id를 함께 넣는다: `/canceled/{단지id}/{거래id}`. 내 판단).

### 4.8 문구 원칙
- "취소됐다", "해제됐다"까지만. "조작", "작전", "가짜" 같은 단어는 쓰지 않는다.
- 페이지 아래 안내: "거래 해제는 대출 불발·계약 합의 해지 등 여러 이유로 생깁니다. 국토교통부 실거래가 공개 자료 기준."

### 4.9 검토에서 나온 세부 (모두 내 판단)
- **"이전"의 뜻**: 계약일이 엄격히 이전(`deal_date <`)인 거래만 비교한다. 같은 날 계약은 비교하지 않는다. "취소되지 않은"은 **지금 시점**의 취소 상태 기준이다. 나중에 이전 거래가 취소되면 판정이 바뀔 수 있고, 그게 맞다(지금 아는 사실 기준).
- **단지 페이지 A의 "최근 1년"**: 해제일 기준(모음 페이지와 같은 기준). D 섹션은 기간 제한 없이 그 단지의 취소 거래 전부를 해제일 최신순으로 보여 준다. A는 요약, D는 전체.
- **공유 주소의 id**: 지금의 거래 id와 단지 id를 쓴다. 정본 DB는 계속 이어서 쓰고 다시 만들지 않는다. 대신 id로 거래를 못 찾으면(단지 병합 등) **단지 페이지로 이동**, 단지도 없으면 **모음 페이지로 이동**한다. 거래는 있는데 취소가 풀렸거나 신고가가 아니면 그 거래 설명만 담담하게 보여 주고 단지 페이지 링크를 둔다.
- **렌더링**: 기존 단지 페이지와 같은 방식. 요청 시 서버에서 그리고 R2 JSON은 fetch 캐시(재검증 1시간). 그래서 카톡 미리보기 메타·OG 이미지가 정상으로 나온다. 빌드 시 정적 생성은 하지 않는다.
- **건수가 적을 때**: 7일 건수가 3건 미만이면 헤드라인과 큰 카드 3장은 **30일 기준**으로 바꿔 보여 준다("최근 30일, 신고가 N건이…"). 30일도 0건이면 헤드라인 대신 "최근 30일 취소된 신고가가 없습니다" 한 줄. 기간 탭을 바꾸면 헤드라인도 그 기간을 따른다.
- **데이터 정리 방법**: `db.migrate`에 멱등 코드로 넣는다(매일 수집이 다운로드 직후 자동 적용 → 사람이 시점을 맞출 필요 없음). 실제 DB 확인 결과 해제일 형식은 `YY.MM.DD` 29,820건, `YYYY-MM-DD` 12,058건 두 가지뿐이고, `is_canceled=1`인데 해제일이 없는 행은 0건.
- **진입점**: 상단 메뉴에 "취소된 신고가" 항목 하나, 홈 화면에는 검색창 아래 통계 카드 줄 근처에 "최근 7일 취소된 신고가 N건" 카드 하나.

## 5. 제약
- 운영비 0원 유지. 새 서버 없음. R2 정적 JSON + Vercel 페이지.
- 기존 구조를 따른다: 파이프라인(Python, `pipeline/`), 프론트(Next 16, `frontend/`), 테스트(pytest, vitest).
- 매일 수집 제한 60분 안에 끝나야 한다. 모음 JSON 계산은 해제일 인덱스로 가볍게.
- 사이트맵에 `/canceled`는 넣는다. 거래별 공유 페이지는 넣지 않는다(내 판단: 수천 개가 얕은 페이지로 잡히면 오히려 손해).

## 6. 빌더에게 맡기는 것
- 컴포넌트 구조, 스타일 세부(기존 Tailwind 톤을 따른다).
- SQL·인덱스 세부. 단, 4.1 정의와 결과가 같아야 한다.
- 주간 재수집을 기존 `collect-daily.yml`에 요일 조건으로 넣을지, 별도 워크플로로 둘지.
- 테스트 범위. 최소한 4.1 정의(경계: 같은 금액은 신고가 아님, 이전 거래 없음, 이전 최고가가 취소 거래인 경우 제외)와 해제일 형식 변환은 테스트로 고정한다.
