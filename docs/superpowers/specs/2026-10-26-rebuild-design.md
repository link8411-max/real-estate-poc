# 수도권 실거래 서비스 재구축 설계

작성일: 2026-10-26
상태: 리뷰 반영, 사용자 승인 대기

## 1. 무엇을, 왜

수도권(서울·경기·인천 78개 시군구) 아파트의 **실거래가(매매·전월세)를 확인하는 서비스**를 다시 세운다.
2026년 1월에 만든 real-estate-poc(FastAPI + SQLite + Next.js)가 기반이다.

지금 서비스의 문제는 기능이 아니라 구조다.

- 백엔드가 Render 무료 플랜에서 1.36GB SQLite를 통째로 들고 있다. 15분 쉬면 잠들고, 깨어날 때 DB를 다시 내려받느라 첫 접속에 1~2분 걸린다.
- 매매만 있고 전월세가 없다. 지도도 없다.
- 2026-04-07 이후 수집이 멈춰 5~8월 데이터가 비어 있다. (GitHub가 60일 비활성 레포의 예약 실행을 끈 것. 10/26에 다시 켰고 9~10월은 채워졌다.)

사용자가 바라는 쓰임새는 두 가지다.

1. **사고 싶은 집과 팔 집의 실거래 추이를 같이 본다.** 호가가 아니라 신고된 거래가 기준.
2. **기존 서비스보다 다시 들어올 이유가 있어야 한다.** 호갱노노처럼 서로 비난하는 댓글판이 아니라, 지역 단위로 서로 응원하는 공간이 되길 바란다.

궁극적으로는 **안드로이드 앱**으로 가고 싶다. 사용자는 안드로이드 개발자다.

## 2. 목표 · 비목표 · 안티목표

### 목표 (이번 설계 범위)
- 매매와 전월세 실거래를 단지·평형 단위로 확인할 수 있다.
- 지도에서 단지를 찾고, 가격·평형·준공·지역 조건으로 걸러서 볼 수 있다.
- 콜드스타트 없이 첫 화면이 1초 안에 뜬다. 서버가 잠들어서 느려지는 구조가 없다.
- 관심단지를 저장하면 새 거래 신고, 시세 대비 싼 거래, 내 집↔사고 싶은 집 차액 변동을 알림으로 받는다.
- 홈 화면에 설치할 수 있는 웹앱(PWA)이고, 알림은 웹 푸시로 온다.
- 서버 API는 나중에 안드로이드 앱이 그대로 쓸 수 있는 형태다.
- 운영 비용 0원을 유지한다. 유료 전환은 사용자가 결정할 때까지 하지 않는다.
- 2026년 5~8월 매매 공백을 채우고, 전월세는 가능한 과거 전체를 받는다.

### 비목표 (지금은 안 함, 자리는 비워둠)
- **매물·호가 수집.** 공공 API가 없고, 포털 크롤링은 법적·기술적 위험이 운영자에게 있다. 출처가 정해질 때까지 보류. 설계에는 "매물이 붙으면 들어갈 자리"만 둔다.
- **지역 커뮤니티.** 다음 단계. 로그인·신고·운영 규칙이 필요하고, 응원하는 문화는 기능이 아니라 운영으로 만들어진다. 이번 설계는 로그인과 사용자 데이터 저장소를 그 전제로 깔아두는 데서 그친다.
- **네이티브 안드로이드 앱.** 다음 단계. 이번에는 API와 알림 로직을 앱이 재사용할 수 있게 만드는 것까지.
- 수도권 외 지역, 아파트 외 주택 유형(오피스텔·빌라), 분양권.

### 안티목표 (이러면 실패)
- 첫 접속이 느린 구조가 남는 것. "무료 플랜이라 어쩔 수 없다"는 결론은 실패다.
- 매달 고정비가 생기는 것.
- 거래가 몇 건이든 전체 데이터를 다시 만들거나 다시 올리는 파이프라인. 하루 3번 돌리면 무료 한도를 넘는다.
- 앱을 붙일 때 서버를 다시 짜야 하는 구조.
- 사용자 데이터(관심단지·알림 조건)를 브라우저 localStorage에만 두는 것. 기기 바꾸면 사라지고 앱으로 못 넘어간다.

## 3. 제약

- 1인 개발. 사용자는 현재 휴직 중으로 시간은 있고 자본은 거의 없다.
- 국토부 API 개발계정은 하루 10,000회. 운영계정 전환은 활용사례 등록이 필요하다.
- 국토부 전월세 API는 **별도 활용신청**이 필요하다 (사용자 할 일).
- Cloudflare R2 무료: 저장 10GB, Class A(쓰기) 월 100만, Class B(읽기) 월 1,000만, 송신 무료.
- Supabase 무료: DB 500MB, 월 송신 5GB, Auth MAU 5만, 프로젝트 2개, **7일 비활성 시 일시정지**. 수집이 하루 3번 DB에 쓰므로 실제로는 정지되지 않는다.
- Vercel Hobby: 서버 함수 무료 범위 안에서 운영. 상업적 용도 금지 조항이 있다. 수익화 시점에 재검토.
- 카카오 로컬 API(주소→좌표) 무료 일 10만 회, 카카오맵 JS SDK 무료 일 30만 회. 2026년 기준 콘솔에서 재확인 필요.
- 기존 자산: SQLite DB 1.6GB(거래 461만 건, 단지 18,611개, 그중 12,933개는 좌표 있음), 수집 스크립트, Next.js 16 프론트(검색·탐색·상세·비교·통계 페이지), GitHub Actions 수집 워크플로, R2 버킷, Vercel 프로젝트.

## 4. 결정된 것

사용자가 정한 것과 내가 판단한 것을 구분한다. **[내 판단]**은 더 나은 안이 있으면 바꿔도 된다.

### 사용자가 정한 것
- 실거래 확인이 뼈대. 매매와 전월세.
- 지도 기반 탐색, 조건 필터·랭킹.
- 매물은 보류. 커뮤니티는 다음 단계. 궁극적으로 앱.
- 리텐션 장치를 하나 가져간다.

### 내 판단
- **리텐션 장치 = 관심단지 알림 3종.** ① 관심단지에 새 거래 신고 ② 그 평형 최근 3개월 평균보다 5% 이상 싼 거래 신고(기존 "급매 배지" 로직을 알림으로) ③ "내 집"과 "사고 싶은 집"을 짝지어 두면 양쪽 거래가 들어올 때마다 차액 변동 알림. ③은 사용자가 "사고 싶은 집과 팔 집 추이를 같이 봤다"고 한 데서 나왔다. 호갱노노에는 없다.
- **Render 제거.** 서버가 DB를 통째로 들고 있는 구조를 없앤다.
- **거래내역은 R2 정적 JSON, 요약·좌표·사용자 데이터는 Supabase Postgres.** 450만 건을 Postgres에 넣으면 500MB를 바로 넘는다. 단지별 전체 거래내역은 단지당 파일 하나로 R2에 두고(측정: 18,611개 합계 gzip 31MB, 중앙값 0.7KB, 최대 28KB), Postgres에는 단지당 요약 1행만 둔다.
- **API는 Next.js Route Handler(Vercel 서버 함수).** 별도 백엔드 프로세스를 두지 않는다. DB를 들고 있지 않으니 콜드스타트가 1초 안이다. `/api/v1/*` 경로에 두고 JSON 응답 계약을 문서화해서 앱이 그대로 쓴다.
- **지도는 카카오맵 JS SDK.** 국내 지도 품질과 무료 한도가 넉넉하다. 대안(MapLibre + VWorld 타일)은 빌더가 카카오 약관이나 한도에서 문제를 발견하면 바꿔도 된다.
- **좌표는 카카오 로컬 API로 채운다.** 지번 주소(동 + 지번)가 전 단지에 있다. 남은 5,678개 + 신규 단지. 하루 10만 회 한도 안.
- **인증은 Supabase Auth. Google 로그인 + 이메일로 시작한다.** (사용자 결정) 카카오 로그인은 카카오가 이메일 제공을 비즈 앱(사업자 등록)에만 허용해서 지금은 못 붙인다. 비즈 앱이 가능해지면 추가하되, 2단계 출시 조건은 아니다. 커뮤니티와 앱에서 같은 계정을 쓴다.
- **웹 푸시(VAPID).** 수집이 끝난 뒤 같은 GitHub Actions 작업이 알림 조건을 평가해서 보낸다. 별도 서버 없음. 안드로이드 Chrome에서 동작. iOS Safari는 홈 화면 설치 후에만 되므로 비목표.
- **수집은 GitHub Actions 유지.** 하루 3번. 60일 비활성으로 꺼지는 문제는 워크플로가 매 실행마다 레포에 작은 상태 파일을 커밋해서 막는다. (GitHub는 커밋이 있으면 활성으로 본다.)
- **수집 작업용 원본 SQLite는 유지.** R2에 보관하고 Actions가 내려받아 쓴다. 중복 판정, 백필, 재생성의 기준이다. 서비스는 이 파일을 읽지 않는다.
- **기존 Next.js 프론트를 고쳐 쓴다.** 새로 만들지 않는다. 페이지 구조와 차트는 유지하고, 데이터 소스만 R2/API로 바꾸고 지도·필터·전월세·관심단지 화면을 더한다.
- **면적 표기는 ㎡ 기본, 평 병기.** 공공 데이터가 ㎡다. 평형 그룹은 전용면적을 3.3058로 나눠 반올림한 평수로 묶는다(예: 84㎡ → 25평... 이 아니라 사용자 인식에 맞춰 59→"24평형", 84→"34평형"처럼 공급면적 관용 표기를 쓸지는 빌더가 기존 코드의 area_stats 묶음 방식을 따른다).
- **정본 SQLite는 R2 사본이다.** 2026년 2월 이후 데이터는 R2 사본에만 있다. 로컬 `real_estate.db`(2026-01-21까지)는 좌표 12,933개를 가진 유일한 사본이므로, 1단계 첫 작업은 **R2 사본에 로컬의 좌표를 (lawd_cd, dong, jibun, name) 키로 이식**하는 것이다. R2 사본에 이미 좌표가 있으면 이 단계는 건너뛴다. 이식 후 로컬 사본은 백업으로만 둔다.
- **apt_id는 한 번 발급되면 영구 불변이다.** R2 경로, Supabase, URL, 관심단지가 모두 이 id를 키로 쓴다. 나중에 같은 단지가 둘로 갈라진 걸 발견해 병합하더라도 id를 재부여하지 않고 `apartment_aliases(old_id → canonical_id)` 테이블로 처리한다. R2에는 old_id 경로에 `{redirect: canonical_id}` 파일을 남긴다.
- **갈아타기 차액은 명시적 짝으로 저장한다.** `gap_pairs(user_id, own_apt_id, own_area, want_apt_id, want_area)`. own·want 모두 평형 필수(평형 없이는 차액이 안 나온다). 한 사용자가 짝을 여러 개 둘 수 있다. `watchlist.role`은 `own | want | watch` 표시용으로 유지하되, 차액 계산은 gap_pairs만 본다. **기준가는 평형별 최근 3개월 평균**(기존 `area_stats.recent_avg`). 3개월 안에 거래가 3건 미만이면 최근 1건으로 대체하고 알림 문구에 "최근 거래 1건 기준"을 붙인다. 1건 이상치로 알림이 튀는 것을 막기 위해서다.
- **레포는 그대로 쓴다.** `~/.gemini/antigravity/scratch/real-estate-poc`. 경로가 이상하지만 git 이력이 있고, 옮기는 건 `mv` 한 번이라 사용자가 원할 때 하면 된다.

## 5. 구조

```
[국토부 API 매매·전월세] ──┐
                          ▼
            GitHub Actions (하루 3회 + 수동 백필)
              1. R2에서 원본 SQLite 내려받기
              2. 이번달·지난달 매매/전월세 수집 → SQLite에 저장
              3. 변경된 단지만 골라서
                 a. R2에 단지 JSON 다시 올림 (매매 1개 + 전월세 1개)
                 b. Supabase 단지 요약 행 갱신
              4. 지역 통계·랭킹 JSON 재생성 → R2
              5. 알림 조건 평가 → 웹 푸시 발송
              6. SQLite를 R2에 다시 올림, 상태 파일 커밋
                          │
         ┌────────────────┼────────────────┐
         ▼                ▼                ▼
   R2 (정적, CDN)    Supabase Postgres    (웹 푸시 → 사용자 기기)
   - 단지별 거래내역  - 단지 요약·좌표
   - 지역 통계/랭킹   - 사용자·관심단지
   - 검색 인덱스      - 알림 조건·푸시 구독
         ▲                ▲
         │                │
         └──── Next.js on Vercel ────┘
               - 페이지 (SSR/정적)
               - /api/v1/* (지도 범위 조회, 필터, 관심단지 CRUD, 푸시 구독)
               - PWA (manifest, service worker)
```

### 5.1 수집
- 매매: 기존 `collect_daily.py` 유지. 대상 월 = 이번달·지난달.
- 전월세: 같은 패턴으로 `RTMSDataSvcAptRent` 수집기 추가. 보증금·월세·계약구분(신규/갱신)·계약기간·갱신요구권 사용·이전 보증금/월세를 저장한다. 동/호는 제공되지 않는다.
- 단지 매칭: 매매와 전월세는 (lawd_cd, dong, jibun, 단지명)으로 같은 apartments 행에 붙인다. 이름 표기가 다른 경우의 처리(공백·괄호 차이)는 빌더가 정한다. 매칭 실패는 로그로 남기고 새 단지로 만든다.
- 백필: `workflow_dispatch`에 시작월·끝월·종류(매매/전월세) 입력을 받는 수동 실행. 매매 2026-02~08(78×7=546회), 전월세 전 기간(78×약 180개월≈14,000회, 개발계정 한도상 2일에 나눠서).
- 비활성 방지: 매 실행 끝에 `data/last_run.json`을 커밋한다.
- 좌표: 수집 후 좌표 없는 단지를 카카오 로컬 API로 채우는 단계를 넣는다. 실패한 단지는 `geocode_quality`에 사유를 남기고 지도에서 빼되 목록·검색에는 나온다.

### 5.2 R2 파일 레이아웃 (공개 읽기, 커스텀 도메인 또는 r2.dev)
```
/v1/apt/{apt_id}/trade.json    매매 거래내역 전체 (취소 거래는 취소일 포함, 제외하지 않음)
/v1/apt/{apt_id}/rent.json     전월세 거래내역 전체
/v1/region/{lawd_cd}.json      지역 단지 목록 + 각 단지 요약
/v1/stats/summary.json         전체 지표, 지역별 평균·거래량·전년비, 상승/하락 Top
/v1/search/index.json          전 단지 [id, 이름, 동, 지역코드, 준공] (측정 gzip 243KB)
/v1/meta.json                  데이터 기준 시각, 데이터 범위
```
- 모든 파일은 gzip/brotli 압축 상태로 올리고 `Content-Encoding`과 `Cache-Control: public, max-age=600`을 단다.
- "변경된 단지만" 올리는 기준: 그 실행에서 거래가 insert/update된 apt_id 집합.
- 쓰기 횟수 추정: 하루 수집 2만 건이 걸치는 단지 수천 개 × 2파일 × 3회 ≈ 수만 회/일 → 월 100만 안. 전월세 백필 첫 실행은 전 단지를 올리므로 한 번에 약 4만 회. 문제 없음.

### 5.3 Supabase 스키마 요점
- `apartments` — id, name, lawd_cd, dong, jibun, build_year, lat, lng(geography), household_count(가능하면), 요약 컬럼: 최근 매매가·날짜, 최근 전세가·날짜, 평형별 최근가 JSONB, 3개월 평균, 전고점, 매매 건수, 전월세 건수, 전세가율. 지도·필터·랭킹은 이 테이블만 본다. 약 2만 행.
- `regions` — 78개.
- `profiles` — Supabase auth.users 1:1.
- `watchlist` — user_id, apt_id, area(평형, nullable=전체), role(`own` | `want` | `watch`), created_at.
- `gap_pairs` — user_id, own_apt_id, own_area, want_apt_id, want_area, threshold(기본 3,000만), created_at. 차액 추적은 이 테이블만 본다.
- `apartment_aliases` — old_id, canonical_id. 단지 병합 시에만 행이 생긴다.
- `alert_rules` — user_id, type(`new_deal` | `bargain` | `gap_change`), params JSONB(예: 급매 임계 %, 차액 변동 임계), enabled.
- `push_subscriptions` — user_id, endpoint, keys, user_agent, created_at.
- `alert_log` — 보낸 알림 기록(중복 발송 방지, 나중에 앱 알림함으로 재사용).
- RLS: 사용자 테이블은 본인 행만. apartments/regions는 공개 읽기.
- 용량: 전부 합쳐 수십 MB. 500MB에 한참 못 미친다.

### 5.4 API (`/api/v1/`, Next.js Route Handler)
- `GET /map?bbox=&zoom=&filters…` — 지도 범위 안 단지 요약. 줌이 낮으면 지역 단위로 묶어서 반환.
- `GET /apartments?filters…&sort=&page=` — 필터·랭킹 목록.
- `GET /apartments/{id}` — 요약 1행 (거래내역은 클라이언트가 R2에서 직접 받음).
- `GET /search?q=` — 서버 보조 검색(인덱스 받기 전 첫 검색용). 클라이언트는 index.json을 받은 뒤 로컬 검색으로 전환.
- `GET/POST/DELETE /watchlist`, `GET/PUT /alert-rules`, `POST/DELETE /push-subscriptions` — 로그인 필요.
- 응답은 모두 JSON, 에러는 `{error: {code, message}}`. OpenAPI 문서를 `docs/api/openapi.yaml`로 남긴다 (앱 개발 시 사용).

### 5.5 프론트 화면
기존 페이지를 유지하면서 바꾼다.

| 화면 | 상태 | 변경 |

| `/map` 지도 | **신규** | 카카오맵. 단지 마커에 최근가(매매/전세 토글). 좌측(모바일은 하단 시트) 필터 패널. 줌아웃 시 지역 묶음 |
| `/search` | 유지 | index.json 기반 클라이언트 검색, 초성 검색 |

| `/apartment/[id]` | 변경 | 매매/전세/월세 탭. 평형별 시세, 차트, 거래내역은 R2 파일에서. 전세가율. 관심단지 추가(내 집/사고 싶은 집/그냥 지켜보기) |

### 5.6 알림 흐름
1. 수집 완료 후 "이번 실행에서 새로 들어온 거래" 집합을 얻는다.
2. 그 거래의 apt_id(+평형)가 걸린 watchlist/alert_rules를 조회한다.
3. 규칙별 판정:
   - `new_deal`: 새 거래 있음 → "래미안X 34평 12억 3,000 신고 (10/24 계약)".
   - `bargain`: 새 거래가 같은 평형 최근 3개월 평균보다 N%(기본 5) 이상 낮음 → "시세보다 6% 낮은 거래".
   - `gap_change`: gap_pairs의 own 또는 want 단지·평형에 거래가 들어오면 차액(want 기준가 − own 기준가)을 재계산. 직전 알림 시점 차액과 비교해 변동이 threshold를 넘으면 → "갈아타기 차액 2억 1,000 → 1억 8,000".
4. alert_log에 없는 것만 웹 푸시 발송. 발송 실패(410 Gone)면 구독 삭제.
5. 같은 실행에서 같은 사용자에게 여러 건이면 한 알림으로 묶는다.

### 5.7 단계
- **1단계 — 뼈대 교체 (서비스 중단 없이)**: R2 사본에 좌표 이식, 전월세 수집기, 변경 단지 JSON 생성기, Supabase 스키마와 요약 갱신, 좌표 채우기, 프론트 데이터 소스 교체, `/map`과 필터, 백필 실행. 끝나면 Render 끈다.
- **2단계 — 리텐션**: 로그인, 관심단지, `/my`, 알림 규칙, 웹 푸시, PWA.
- **3단계 (이 설계 밖)**: 커뮤니티, 매물, 안드로이드 앱.

1단계가 끝나면 사용자에게 보여주고 2단계로 간다. 2단계 안에서도 "로그인 + 관심단지 + new_deal 알림"을 먼저 내보내고 bargain·gap_change를 더한다.

## 6. 빌더에게 맡기는 것
- 변경 단지 추적 방식(수집 중 집합 수집 vs 트랜잭션 테이블의 created_at 비교).
- 매매·전월세 단지명 매칭 규칙과 정규화.
- 평형 묶음 기준(기존 코드의 area_stats 방식을 우선 따른다).
- 지도 줌 레벨별 묶음 기준과 마커 디자인.
- 필터 항목의 정확한 집합(최소: 지역, 가격대, 평형, 준공년도, 거래 종류, 최근 N개월 거래 있음).
- 검색 인덱스의 초성 처리 방식.
- Supabase와 Vercel 사이 인증 토큰 전달 방식(쿠키 기반 SSR 권장).
- R2 공개 도메인(r2.dev 서브도메인 vs 커스텀 도메인). 사용자 소유 도메인 `sudogwon.com`이 `.env.local`에 있으나 실제 연결 여부는 미확인.
- 테스트 범위. 최소: 수집기 파싱, 변경 단지 JSON 생성, 알림 판정 로직은 단위 테스트.
- GitHub Actions 30분 제한 안에서 전월세 백필을 나누는 방법.

## 7. 사용자가 해야 할 일 (코드 밖)
1. data.go.kr에서 **아파트 전월세 실거래가 API 활용신청** (매매 키와 같은 계정). 승인 후 키는 같은 키일 수도, 다를 수도 있다. GitHub Secrets에 `MOLIT_RENT_API_KEY`로 넣는다.
2. **Supabase 프로젝트 생성**(무료), URL·anon key·service role key를 Vercel 환경변수와 GitHub Secrets에 넣는다.
3. **Kakao Developers 앱 생성**, JavaScript 키(지도)와 REST API 키(좌표)를 발급받고 Vercel 도메인을 플랫폼에 등록한다. (로그인은 쓰지 않으므로 비즈 앱 전환 불필요.)
3-1. **Google Cloud에서 OAuth 클라이언트 생성**, Supabase Auth의 Google provider에 등록한다.
4. 1단계 완료 후 **Render 서비스 삭제**.
5. GitHub Personal Access Token(1월 발급분) 폐기 — 로컬 remote에 박혀 있던 것. 이미 remote에서는 제거했다.
